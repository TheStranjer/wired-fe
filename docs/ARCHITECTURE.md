# Architecture

Numbered decisions. Tickets and code comments cite them as "decision N". To change one, amend it here in the same commit as the code.

1. **Stack**: React 19 + TypeScript 6 (strict), built by Vite into a static bundle. Node and pnpm versions are pinned in `mise.toml` and `package.json` `packageManager`. TypeScript stays on 6.x until typescript-eslint supports 7.

2. **Deliverable**: `dist/` holds `index.html`, one `wired.[hash].js` and one `wired.[hash].css` (no code splitting), plus the fixed files from `public/`. Asset URLs are relative (`base: './'`), so the bundle can be hosted at any path on any static host.

3. **Build-time configuration**: deployment settings (which instances the build may talk to, defaults, branding) are fixed when the bundle is built, from one typed and validated config file. There is no runtime config fetch. Instance modes:
   - `same-origin`: the backend sits behind the same origin (reverse proxy). The usual deployment.
   - `fixed`: one named origin.
   - `list`: the user picks from a list.
   - `open`: the user may type any instance.

   The CSP `connect-src` is derived from the mode.

4. **Routing**: hash routing (`/#/@lain@wired.example`). WiredFE's URLs can never collide with the backend's content-negotiated ActivityPub URLs (`/users/...`, `/objects/...`, `/notice/...`), and any static host works without rewrite rules for WiredFE's own links. The routes are `#/notice/<id>`, `#/@<user>[@<host>]`, `#/users/<id>`, and `#/tag/<name>` (`src/lib/route.ts`), opened by `src/app/useHashRoute.ts`. wired-be's redirects arrive as paths; one startup step (`pathToHash`, `src/lib/pathRoute.ts`) rewrites them to the hash routes, which needs a host that serves `index.html` for unknown paths (README). The invite link `/registration/<token>` becomes `#/registration/<token>`, which is no window route: `parseRegistrationRoute` (`src/lib/route.ts`) reads it and `src/app/useRegistrationOverlay.tsx` opens the sign-up overlay (`src/features/registration`) with or without a signed-in account, taking the hash out of the address bar. The reset letter's `/password_reset/<token>` becomes `#/password_reset/<token>` the same way; `parsePasswordResetRoute` (`src/lib/route.ts`) reads it and `src/app/usePasswordResetOverlay.tsx` opens the new-password box (`src/features/passwordReset`), which checks the two fields match and sends `POST /api/v1/pleroma/password_reset` (`src/api/endpoints/passwordReset.ts`); the passwords live only in that form and request, and `/forgot <email|nick>` asks for the letter (`POST /auth/password`) without a login. The authorization request `/oauth/authorize?<query>` of a third-party app becomes `#/oauth/authorize?<query>` the same way; `parseAuthorizeRoute` (`src/lib/authorizeRoute.ts`) reads it and `src/app/useAuthorizeOverlay.tsx` opens the authorization box (`src/features/authorize`): the password login first when no account for that instance is signed in, then the app's name, website and permissions with Authorize / Deny, answered by a bearer-authorised `POST /oauth/authorize` whose returned `http(s)` address the browser is sent to (or whose code is shown, for the out-of-band URN). The token never goes into a URL. wired-be's external-login callbacks `/oauth/external/register?state=` and `/oauth/external/consent?state=&confirm_token=` become `#/oauth/external/register?...` and `#/oauth/external/consent?...` the same way; `parseExternalRoute` (`src/lib/externalRoute.ts`) reads them and `src/app/useExternalOverlay.tsx` opens the registration box or the consent box (`src/features/external`). Both are anonymous (no account needs to be signed in): the registration box prefills nickname and e-mail from `GET /oauth/registration_details`, `POST /oauth/register` answers with an address to go to or a wait for approval or e-mail confirmation, and the consent box lists the app and its scopes and posts Authorize or Deny. Addresses the instance returns are only followed when they are http(s) (`src/lib/webUrl.ts`).

5. **Backends: capabilities, not brands.** WiredFE talks to Wired, Mastodon and Pleroma/Akkoma. On connect it reads NodeInfo (`software.name`, `metadata.features`), `/api/v1/instance` and `/api/v2/instance` once, and builds one typed `Capabilities` object. UI and commands check capabilities (`caps.emojiReactions`), never the backend's name; only `src/capabilities` reads the brand. A capability that is advertised but answers 404/501 is treated as absent.

6. **One command registry.** Every user action is a registry entry: name, aliases, argument grammar, required capability, help text, default hotkey, and the handler. The command line, `/help`, tab completion, the keymap and click targets are all generated from it.

7. **Wired's shapes are the internal model.** API responses are parsed with valibot schemas in `src/api`. Mastodon and Pleroma responses go through adapters that map them onto Wired's entity shapes; the rest of the app sees one model.

8. **Auth**: per instance, WiredFE registers an OAuth app at runtime (`POST /api/v1/apps`) and caches its credentials; there is no build-time client secret. Authorization code flow with the redirect URI derived from `window.location`. Tokens are stored per account, keyed by instance origin plus account id, together with the refresh token and the access token's expiry (ms epoch) when the instance issues them; `refreshAccessToken` (`src/api/oauth.ts`) trades a refresh token for a new pair and `AccountStore.updateTokens` stores it. Registering from an invite (`registerAccount`, `src/accounts`) reuses the same app cache: the cached app trades for an app token (`client_credentials`), `POST /api/v1/accounts` carries the invite as `token`, and a token that verifies is stored like a login's; a response (or a refused token) that says the address needs confirming or a moderator must approve stores nothing. The password lives only in the form's state and that one request body. The login the app-authorization box asks for when nobody is signed in (`passwordLogin`, `src/accounts`) uses the `password` grant with the same app cache, and its password too lives only in that form and request. WiredFE's own `/connect` on a same-origin build comes back through that same overlay (WFE-177): `isOwnRequest` (`src/app/ownRequest.ts`) recognises it by a `client_id` equal to the app cached for this origin and page, plus a `redirect_uri` equal to this page or the `state` of the pending login. After the password login (or at once when already signed in) such a request has no consent box: the pending login is cleared, the address bar returns to the page's path and the overlay closes, with the account's windows opened by the login itself. Other apps' requests still get the box.

9. **Default assets contract**: Wired builds its default avatar, banner, instance thumbnail and mascot URLs against its `FRONTEND_BASE_URL` (WBE-304). WiredFE ships those files at fixed paths under `images/`: `avi.png`, `banner.png`, `thumbnail.jpg`, `mascot.png`. They are generated at build time by the Vite plugin in `tooling/images` (pixel-art grids, pure-JavaScript PNG/JPEG encoders) and emitted into `dist/images/`; the dev server serves the same URLs from memory. The files are not stored in `public/`. Renaming one breaks every Wired instance's defaults.

10. **Security posture**: strict CSP written into `index.html` at build time; no third-party origins at runtime; remote HTML rendered only through one sanitizing component; network and storage access confined to their owning modules (ESLint enforces it).

11. **Testing**: Vitest + Testing Library for units (jsdom), recorded per-backend fixtures for API adapters, Playwright against the production build for flows. No test waits on real time. The end-to-end suite also runs axe-core over every main screen — a `serious` or `critical` violation fails the gate (AGENTS.md "Accessibility is not optional") — and writes one review PNG per screen per theme to `test-results/screens/`; those images are for human review, never compared against a baseline.

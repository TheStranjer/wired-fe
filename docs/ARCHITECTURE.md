# Architecture

Numbered decisions. Tickets and code comments cite them as "decision N". To change one, amend it here in the same commit as the code.

1. **Stack**: React 19 + TypeScript 6 (strict), built by Vite into a static bundle. Node and pnpm versions are pinned in `mise.toml` and `package.json` `packageManager`. TypeScript stays on 6.x until typescript-eslint supports 7.

2. **Deliverable**: `dist/` holds `index.html`, one `wired.[hash].js` and one `wired.[hash].css` (no code splitting, but for one `emoji.[hash].js` chunk: the Unicode emoji list, a dynamic `import()` the emoji picker makes the first time it opens, WFE-265), plus the fixed files from `public/` (today only `favicon.png`, the icon `index.html` declares). Asset URLs are relative (`base: './'`), so the bundle can be hosted at any path on any static host. Under a sub-path, the build config's optional `basePath` (e.g. `/fe/`) tells `pathToHash` which prefix of wired-be's redirect paths to strip (decision 4).

3. **Build-time configuration**: deployment settings (which instances the build may talk to, defaults, branding) are fixed when the bundle is built, from one typed and validated config file. There is no runtime config fetch. Instance modes:
   - `same-origin`: the backend sits behind the same origin (reverse proxy). The usual deployment.
   - `fixed`: one named origin.
   - `list`: the user picks from `origins`. With `allowCustom: true` (default `false`) they may also type any other instance. An empty `origins` is valid only with `allowCustom: true`; an empty list that forbids custom instances fails the build.
   - `open`: the user may type any instance. The same as a `list` with no origins and `allowCustom: true`.

   The CSP `connect-src` is derived from the mode (a `list` with `allowCustom` allows any secure origin, like `open`).

On a `list` build the visitor picks rather than types: the login, sign-up and new-password boxes offer the listed origins as radio choices named by their bare host (`src/ui/InstanceChoices.tsx`), with a free-text "Other instance" field only when `allowCustom` is set (a lone origin is preselected), and `/connect` Tab-completes its argument from the same list as hosts, each a suggestion row to click (`src/commands/connectWords.ts`). An `open` build, or a list with no origins, keeps the free-text field and offers no completion.

The optional `defaultLocale` (a BCP 47-style code) is the UI language of readers who have not chosen one, ahead of the browser's languages (decision 19). The schema checks its shape; `tooling/loadConfig.ts` fails the build unless it is one of `SUPPORTED_LOCALES`, so a typo cannot ship.

4. **Routing**: hash routing (`/#/@lain@wired.example`). WiredFE's URLs can never collide with the backend's content-negotiated ActivityPub URLs (`/users/...`, `/objects/...`, `/notice/...`), and any static host works without rewrite rules for WiredFE's own links. The routes are `#/notice/<id>`, `#/@<user>[@<host>]`, `#/users/<id>`, and `#/tag/<name>` (`src/lib/route.ts`), opened by `src/app/useHashRoute.ts`. wired-be's redirects arrive as paths; one startup step (`pathToHash`, `src/lib/pathRoute.ts`) rewrites them to the hash routes, which needs a host that serves `index.html` for unknown paths (README). The invite link `/registration/<token>` becomes `#/registration/<token>`, which is no window route: `parseRegistrationRoute` (`src/lib/route.ts`) reads it and `src/app/useRegistrationOverlay.tsx` opens the sign-up overlay (`src/features/registration`) with or without a signed-in account, taking the hash out of the address bar. The reset letter's `/password_reset/<token>` becomes `#/password_reset/<token>` the same way; `parsePasswordResetRoute` (`src/lib/route.ts`) reads it and `src/app/usePasswordResetOverlay.tsx` opens the new-password box (`src/features/passwordReset`), which checks the two fields match and sends `POST /api/v1/pleroma/password_reset` (`src/api/endpoints/passwordReset.ts`); the passwords live only in that form and request, and `/forgot <email|nick>` asks for the letter (`POST /auth/password`) without a login. The authorization request `/oauth/authorize?<query>` of a third-party app becomes `#/oauth/authorize?<query>` the same way; `parseAuthorizeRoute` (`src/lib/authorizeRoute.ts`) reads it and `src/app/useAuthorizeOverlay.tsx` opens the authorization box (`src/features/authorize`): the password login first when no account for that instance is signed in, then the app's name, website and permissions with Authorize / Deny, answered by a bearer-authorised `POST /oauth/authorize` whose returned `http(s)` address the browser is sent to (or whose code is shown, for the out-of-band URN). The token never goes into a URL. wired-be's external-login callbacks `/oauth/external/register?state=` and `/oauth/external/consent?state=&confirm_token=` become `#/oauth/external/register?...` and `#/oauth/external/consent?...` the same way; `parseExternalRoute` (`src/lib/externalRoute.ts`) reads them and `src/app/useExternalOverlay.tsx` opens the registration box or the consent box (`src/features/external`). Both are anonymous (no account needs to be signed in): the registration box prefills nickname and e-mail from `GET /oauth/registration_details`, `POST /oauth/register` answers with an address to go to or a wait for approval or e-mail confirmation, and the consent box lists the app and its scopes and posts Authorize or Deny. Addresses the instance returns are only followed when they are http(s) (`src/lib/webUrl.ts`).

5. **Backends: capabilities, not brands.** WiredFE talks to Wired, Mastodon and Pleroma/Akkoma. On connect it reads NodeInfo (`software.name`, `metadata.features`), `/api/v1/instance` and `/api/v2/instance` once, and builds one typed `Capabilities` object. UI and commands check capabilities (`caps.emojiReactions`), never the backend's name; only `src/capabilities` reads the brand. A capability that is advertised but answers 404/501 is treated as absent. The detected profile is cached per origin in `sessionStorage` (`capabilities/profileCache.ts`), so a reload does not detect again; `/connect` and a 404/501 from a capability-gated request drop the cached entry.

6. **One command registry.** Every user action is a registry entry: name, aliases, argument grammar, required capability, help text, default hotkey, and the handler. The command line, `/help`, tab completion, the keymap and click targets are all generated from it. An entry's `requires` names the capability flags (decision 5) the backend must carry; for the active account the help, completion, keymap and `/binds` list only the entries it can do, and typing a hidden one prints why it is refused. `/help <command>` prints one entry; `/help layout`, `/help feeds` and `/help sync` print a topic (`src/commands/helpTopics.ts`): a name, one paragraph and the canonical names of the commands it covers, whose summary lines are read from the registry. A topic name typed without a slash wins over a command of the same name (`/help sync`; `/help /sync` is the command), and a test fails when a topic lists a command the registry lacks. While the first word of the line is being typed, a suggestion list above the command line shows the matching commands as `/name (/alias) — summary`, eight rows and a dim `+N more` (`src/commands/suggest.ts`); it reads the same candidates Tab completes and the same registry summaries, Tab steps its highlight, a click completes to a row, and a `Provider` that has a `describe` function fills it, so later word kinds slot in without reshaping it. The list also opens for the `@handle`, `#tag` and `:emoji:` word at the caret anywhere on the line (`src/views/completionProviders.ts`): a handle is described by its display name (plain text, never HTML), a tag by nothing, an emoji by its image. For an `@handle` of at least two characters, after a 250 ms pause the active account's instance is asked once for matching accounts (`src/views/useHandleSearch.ts`, `type: 'accounts'`, errors silent) and the answers are listed below the handles the buffers showed, without repeats.

7. **Wired's shapes are the internal model.** API responses are parsed with valibot schemas in `src/api`. Mastodon and Pleroma responses go through adapters that map them onto Wired's entity shapes; the rest of the app sees one model.

8. **Auth**: per instance, WiredFE registers an OAuth app at runtime (`POST /api/v1/apps`) and caches its credentials; there is no build-time client secret. Authorization code flow with the redirect URI derived from `window.location`. Tokens are stored per account, keyed by instance origin plus account id, together with the refresh token and the access token's expiry (ms epoch) when the instance issues them; `refreshAccessToken` (`src/api/oauth.ts`) trades a refresh token for a new pair and `AccountStore.updateTokens` stores it. Registering from an invite (`registerAccount`, `src/accounts`) reuses the same app cache: the cached app trades for an app token (`client_credentials`), `POST /api/v1/accounts` carries the invite as `token`, and a token that verifies is stored like a login's; a response (or a refused token) that says the address needs confirming or a moderator must approve stores nothing. The password lives only in the form's state and that one request body. The login the app-authorization box asks for when nobody is signed in (`passwordLogin`, `src/accounts`) uses the `password` grant with the same app cache, and its password too lives only in that form and request. WiredFE's own `/connect` on a same-origin build comes back through that same overlay (WFE-177): `isOwnRequest` (`src/app/ownRequest.ts`) recognises it by a `client_id` equal to the app cached for this origin and page, plus a `redirect_uri` equal to this page or the `state` of the pending login. After the password login (or at once when already signed in) such a request has no consent box: the pending login is cleared, the address bar returns to the page's path and the overlay closes, with the account's windows opened by the login itself. Other apps' requests still get the box.

9. **Default assets contract**: Wired builds its default avatar, banner, instance thumbnail and mascot URLs against its `FRONTEND_BASE_URL` (WBE-304). WiredFE ships those files at fixed paths under `images/`: `avi.png`, `banner.png`, `thumbnail.jpg`, `mascot.png`. They are generated at build time by the Vite plugin in `tooling/images` (pixel-art grids, pure-JavaScript PNG/JPEG encoders) and emitted into `dist/images/`; the dev server serves the same URLs from memory. The files are not stored in `public/`. Renaming one breaks every Wired instance's defaults.

10. **Security posture**: strict CSP written into `index.html` at build time; no third-party origins at runtime; remote HTML rendered only through one sanitizing component; network and storage access confined to their owning modules (ESLint enforces it).

11. **Testing**: Vitest + Testing Library for units (jsdom), recorded per-backend fixtures for API adapters, Playwright against the production build for flows. No test waits on real time. The end-to-end suite also runs axe-core over every main screen — a `serious` or `critical` violation fails the gate (AGENTS.md "Accessibility is not optional") — and writes one review PNG per screen per theme to `test-results/screens/`; those images are for human review, never compared against a baseline.

12. **Desktops, panes, floats.** A _window_ stays what it is today (`src/windows`: one view of one thing with one buffer). A _pane_ shows one window in a desktop's split tree; a _float_ shows one window in a free rectangle above the tree; a _desktop_ is one split tree plus its floats. Panes reference windows by id; a window may be shown in several panes or in none (hidden, like a vim buffer). The layout state is pure and lives in `src/windows` (`splitTree.ts`, `floats.ts`, `desktops.ts`). The tree is binary: a leaf `{ paneId, windowId }` or a split `{ dir: 'row' | 'column', ratio, a, b }`; `row` is side by side (vim `:vsplit`, tmux `%`, "vertical split"), `column` is stacked (`:split`, tmux `"`, "horizontal split"). Float rectangles are fractions of the viewport (0..1), clamped inside it. One pane or float per desktop has focus; its window is `windows.activeId`, so existing commands keep acting on "the active window". Desktops are numbered from 1 with no upper bound. Dragging a float's title bar with Shift held previews, and on release performs, docking it against the nearest edge of the tree pane under the pointer (`dropZone`, `dockAt`: `row` for left/right, `column` for top/bottom, the float's pane in `a` for left/top). `/pop [label]` (hotkey `p`, or a double-click on a post) opens the post's thread window in a new float, unless the reader is already in that thread (an info line says so) or its window is already shown on the desktop (that pane or float is focused instead). On a mobile device class only the focused pane or float is drawn, full size, and the title bar carries a `‹ 2/4 ›` pane switcher in place of the pane buttons (decision 17).

13. **Every view is a window kind.** Feeds, the composer and the people list are window kinds beside home, thread, dm and the rest. The pane frame around them is the same for all. Where a newly opened window goes is its _placement_: `here` (the focused pane), `vsplit`, `split`, `float` or `hidden`; commands that open windows accept `--in <placement>` and a setting holds the default. The choice is made in one place: `--in`, else the per-kind setting, else the default (`resolvePlacement`, `src/state/placement.ts`). `/home`, `/local`, `/federated`, `/notifications`, `/tag`, `/search`, `/whois`, `/query` (`/dm`), `/thread` and `/compose` (also `/composer`) are wrapped in `placedRun` (`src/commands/openWindowRun.ts`), which cuts a trailing `--in` off the arguments and places the `open` the command asks for; a command does not spell placement itself. `here` is the plain open; the others are the `openPlaced` app action (`placeReducer`, `src/state/placeAction.ts`): the window joins the list without becoming active and `placeWindow` shows it (`vsplit` and `split` split the focused pane, `float` splits and tears off, `hidden` shows nothing). The settings are `openIn` (default `here`, `/set openIn float`) and `openInByKind`, set with the dotted form `/set openIn.thread vsplit` (`default` takes a kind's choice back). `/compose [text]` (`Ctrl+E`, `c`) is the only way to the composer: the modal overlay is gone. It opens a composer window holding the text, or focuses the open composer whose draft is still empty; with no text it takes the command line's own plain text. A composer defaults to `float` (it pops up over the feed), a default `resolvePlacement` holds for the kind, so `/set openIn.composer here` or `--in` places it elsewhere and `openIn` alone does not move it. `/attach` while a composer is focused puts the files in that composer's media, not in the pending list. Otherwise the pending media are lines of the same slice (`composerMedia`) under the reserved `COMMAND_LINE_MEDIA` key: the `[📎]` button at the left of the command line opens the file input `/attach` opens, the tray above the command line (`src/app/CommandTray.tsx`, the composer's own `AttachmentList`) shows a row per file, and `[+N media]` in the status line focuses the first description. Alt text typed there is put with `describeMedia` just before the post (only when it differs from what the file went up with), and a refusal blocks the post and keeps the media. `/media [label] [n]` (`v`) opens the `media` window of a post's n-th attachment (`{ kind: 'media', accountKey, target: '<statusId>:<n>' }`, `src/state/mediaWindow.ts`, `src/features/media`): the full-size file fitted to the pane, with its description, `n/N`, `‹`/`›` to step (which open the sibling in the same pane and close the window stepped from) and an Open original button that runs `/open <url>` through the line runner. The window fetches its post itself, so a restored desk shows it, and a sensitive post waits behind its cover. It has a `float` default of its own (the built-in per-kind table `KIND_DEFAULTS` in `src/state/placement.ts`), under `openIn.media` and `--in`. `/people` has its own default, a split to the right, so only `--in` or `openIn.people` places it; `/vsplit`, `/split` and `/float <view>` place their window themselves and run the open command with `placedByCaller`, which turns placement off. Openings that are not typed commands are placed too: a click on a nick, a mention or hashtag in a body, a notification's actor or excerpt, or a name in the people list opens its window by `placementFromClick(click, configured)` (`src/state/placementFromClick.ts`), where `configured` is the kind's setting or the default: a plain click follows it, **Ctrl/Cmd+click** opens a `float`, **Shift+click** a `vsplit`, **middle-click** a `hidden` window, and the browser never opens a tab for an internal link. `clickOpen` turns that into the plain open (`here`) or `openPlaced`. The `t` hotkey is `/thread`'s binding, so it follows the settings like the command. A hash route (`useHashRoute`, `openRoute`) always opens `here`. A reply composer is placed by `openReplyWindow` (same file): `--in`, else `openIn.composer`, else the `replyIn` setting (default `split`), never the global default. `/reply a3` with no text opens it: a `composer` window bound to the post (`ComposerFields.inReplyTo`: the status and the line's account key, decision 14), whose fields `replyFields` (`src/state/replyDraft.ts`) fills with the mentions, the post's audience capped by the default and its content warning; it posts as that account with `in_reply_to_id` and closes its window after sending. The card's reply button and `Shift+r` run `/reply a3`; `r` still prefills the line (`/quote` moved to `q`). `/quote a3 text` creates its status itself as the quoted post's account (`createStatus` with `quote_id`, never the active window's `onPost`, so it works from a feed, notifications, a profile or a thread); with no text, the card's quote button and `Shift+c` (`Shift+q` is `/close`) open a composer bound to the post (`ComposerFields.quoteOf`) that sends with `quote_id` and closes after sending. `/edit a3` with no text, and the card's `⋯` → Edit, open a third bound composer (`ComposerFields.editing`, placed like the reply one): it reads `GET /api/v1/statuses/<id>/source` for the plain text and content warning, shows `editing [a3]` with the original's excerpt, locks the visibility select (an edit cannot change it) and offers no attachments or poll; its send is `editPost` (`src/state/editPost.ts`, a `PUT` carrying `editFields` for the media and poll the post keeps), which updates the post in every buffer, closes the window and prints `✎ edited [a3]` in the status window. `e` still prefills `/edit a3 `, and `/edit a3 <text>` sends at once.

14. **Feeds.** A feed is a saved `FeedSpec`: an id, a name and sources `{ accountKey, source }`, source one of `home`, `mentions`, `dms`, `notifications`, `local`, `federated`, `tag:<name>`. A feed window merges its sources newest first and shows a post seen by several accounts once (by URI). Every post and notification line carries the key of the account that fetched it; commands acting on a line act as that account, falling back to the window's account. A feed window is `{ kind: 'feed', accountKey: null, target: <feed id> }`, titled with the feed's name: it fetches the first page of every source in parallel, shows the merge up to the paging boundary, and pages older only the sources that hold that boundary back; a source that fails prints one client message and is skipped. Feeds are live too: each source joins the stream that carries it on its own account's one shared connection (`user`, `user:notification`, `direct`, `public:local`, `public`, `hashtag`), and streamed posts and notifications merge into the window's kept feed like a fetched page, so a post two accounts hear is one line; edits and deletes reach the kept feed as they reach the lines. The `/feed` commands manage feeds, and the window kind `feedEditor` (`{ kind: 'feedEditor', accountKey: null, target: <feed id> | 'new' }`, `src/features/feedEditor`) is their GUI: a name field, a table of signed-in accounts by source kinds, per-account hashtag chips, `[ save ]` and an inline-confirmed `[ delete feed ]`. Saving runs the equivalent `/feed` lines through the line runner the command line lends the views (`src/views/LineRunnerContext`, `src/commands/runLines`), so command, click and settings stay one path and the commands' refusals are shown inline. `/feed edit <name>`, a bare `/feed new` and the `✎` button in a feed pane's header open it; saving a new feed opens the feed in the editor's pane. The first run makes a feed named `stream` (`src/state/streamFeed.ts`): `*:home`, `*:mentions`, `*:dms`, `*:notifications`, flagged `auto: true`, opened alone in desktop 1's pane with the status window hidden behind it and no per-account home windows. That happens once: when no feeds are saved and the settings flag `streamMade` (hidden from `/set`) is unset, with no saved desk to restore; the flag stays set when the reader deletes `stream`, so it is never made again, and a reader who already has feeds is not touched. While `auto` holds, an account that signs in later (the `signedIn` action, or startup after a login redirect) gets its four sources added; any `/feed` edit (`add`, `rm`, `rename`) clears `auto`, after which a newcomer only earns the hint `/feed add stream @new@x:home …` and its own home and notifications windows. Signing an account out takes its sources out of every feed.

15. **Cards and lines.** A window renders posts as cards (default) or IRC lines and shows or hides avatars and images, from the settings `density`, `avatars`, `images`, each overridable per window. Images load from remote instances (the CSP already allows `img-src https:`); nothing autoplays; sensitive media stays covered until opened. A `direct` card carries a `✉ DM from → to` header, a dashed border and the accessible name "Direct message …"; in a DM window cards are compact chat bubbles, the viewer's own right-aligned as `you`, with a run of one author's messages within five minutes sharing one header.

16. **Pseudomonochrome.** The default `wired` theme is near-black with grey-white text; lime is reserved for borders and the accent. The focused thing glows: the focused pane or float, and whatever holds focus on top of it (dialogs, open menus, the emoji picker), has the bright accent border (`--color-border-focus`); unfocused panes, split gutters, title-bar rules and other chrome use a dimmer version (`--color-border-idle`). Each stays at least 3:1 against the background and the two stay visibly distinct. Focus is never shown by colour alone: the focused pane's title also carries `[*]`. Decision 11's contrast rules still hold.

17. **Persistence and sync.** Desktops, floats, open windows, feeds and settings are saved through `src/storage` per _device class_ (`desktop`: Windows, macOS, Linux, ChromeOS; `mobile`: Android, iOS, iPadOS) and synced through the Pleroma settings store (`GET`/`PATCH /api/v1/pleroma/settings/wired-fe`, served by Wired, Pleroma and Akkoma; capability `settingsStore`). A _primary_ account chosen by the user, with ordered fallbacks, holds the synced copy: the first whose backend has `settingsStore` and whose token works. The server copy is `{ version: 1, desktop?: Snapshot, mobile?: Snapshot }`; each snapshot has an `updatedAt` and the newer one wins. Accounts without the capability keep state locally only. Which account is primary is a local-only choice (`syncAccounts`, ordered account keys, and `syncEnabled`, under the `sync` namespace of `src/storage`; `src/accounts/syncPrefs.ts`), never synced since it decides where sync goes: `pickSyncAccount` (`src/state/syncAccount.ts`) takes the first listed account that is signed in, not expired and has `settingsStore` (with an empty list, the first such account), and nothing when sync is off. `/sync` edits it; signing an account out removes it from the list. The local copy is the desk snapshot (`src/state/deskSnapshot.ts`, schema in `deskSchema.ts`, version 1): every open window except status (id, title, ref, display overrides) and the desktops (trees, floats, focus, active desktop, pane counter), all as arrays; buffers, unread counts and scroll positions are never saved. It lives in the `desk` store of `src/storage` under the device class (`wired:v1:desk:<deviceClass>`), written 500 ms after the windows or layout last changed and only once startup has restored (`useDeskPersistence`). Startup restores it after the accounts load, dropping windows of accounts that are not signed in and the panes showing them (`fromSnapshot`), and then opens no default windows; a missing, corrupt or old-version snapshot is ignored. **The sync engine** (`useDeskSync`, `src/app/deskSyncEngine.ts`; pure helpers in `src/state/deskSync.ts`) keeps this device class's key of the server document equal to the local desk. A synced snapshot is the desk snapshot plus the whole `Settings` and its own `updatedAt`; only the current device class's key is read or written, and every collection inside is an array, so a `PATCH` of `{ [deviceClass]: snapshot }` replaces it under the server's deep merge. The local stamp (`src/app/deskStamp.ts`) is the moment the desk or settings last changed here or were last taken from the server. _Pull_ runs once startup is ready and on `/sync now` or any change of the `/sync` choices: `pickSyncAccount` names the account, the server's snapshot is validated, and `decideSync` applies it when its `updatedAt` is newer than the stamp, keeps the local desk and schedules a push when it is older or missing, and ignores it with one warning when it does not parse. _Push_ runs 3 s after the last change to the windows, desktops or settings (a pull that applied the server's desk is not a change); a primary not pulled from yet is pulled from first. A failure keeps the session working locally and prints one warning per error kind (`tooLarge`, `forbidden`, network, ...) per session; the next change retries. The server caps the whole settings store (all apps, both device classes) at 1 MiB, so a push is first measured in UTF-8 bytes against a budget of 384 KiB per device class (`fitSnapshot`, `src/state/deskFit.ts`); over it, the synced copy alone leaves out, in order, windows no pane or float shows, empty desktops (never the active one) and key overrides past 200, with one warning naming what was left out (the local desk keeps everything), and when that is not enough nothing is pushed and one warning says sync is paused. A 422 `tooLarge` anyway (other apps filled the store) halves the budget once and retries; a second one is the usual `tooLarge` warning. A 404/501 drops the account's `settingsStore` capability and the sync goes quiet; an account without the capability never sees a request. `/sync` also prints the last pull, the last push and the last error, and the status line shows `⇅` while a push waits and `⇅!` after an error. Tokens and snapshot contents are never logged. On mobile one pane shows at a time, full screen, with a pane switcher.

18. **Key sequences and default keysets.** A binding is a sequence of one or more chords (`Ctrl+B %`, `w v`). After a prefix the keymap waits for the next key; `Esc` or an unbound key cancels. Browsers reserve `Ctrl+W`, `Ctrl+T`, `Ctrl+N`, so they are never defaults. Defaults: tmux-style in both modes (`Ctrl+B` then `%` vsplit, `"` split, arrows focus, `o` next pane, `x` close pane, `z` only, `c` new desktop, `&` close desktop, `n`/`p` next/previous desktop, `0..9` jump to a desktop (`0` is 10), `f` float, `d` dock, `I` (Shift+i) `/attach`, which opens the file dialog, `Space` `/start`, which opens the start menu, `L` (Shift+l) `/lang --pick`, which opens the list of interface languages); vim-style in navigation mode (`w` then `v`, `s`, `h/j/k/l`, `w` next pane, `x` swap right, `c` close pane, `o` only, `=` equalize, `f`, `d`; `/whois` moves from `w` to `Shift+w`; `Shift+i` is `/attach`; `w Space` is `/start`; `Shift+l` is `/lang --pick`); `Alt+1..9` (and `Alt+0` for 10) jump to a desktop, `Alt+[`/`Alt+]` step left/right, wrapping from 1 to the last. A desktop is made (stepping right past the last, `/desktop new` or `Ctrl+B c`, or a jump to the number just past the end) only when the last desktop is not empty (`canAppendDesktop`, `appendRefusal` in `src/windows/desktopAppend.ts`); a jump further past the end makes nothing. Otherwise the reducer leaves the state unchanged and the command fails with a message, which the error alert shows (`Desktop 19 is empty: put something on it before making another`). Moving between existing desktops is never refused. Closing a desktop (`/desktop close [n]`, `Ctrl+B &`, the `×` after the active desktop's marker in the status line while there are two or more, or a middle-click on any marker) drops its panes but no window, which stays open and listed in `/win`; the last desktop is never closed. `/desktop prune` closes every empty desktop (no tree, no floats) except the active one in one reducer step (`pruneDesktops`). The start menu is the one place that opens a view as a float: the `[≡ wired]` button at the left of the status line (`src/app/StartMenu.tsx`), opened by `/start` (the `startMenu` flag of the app state), lists the views of the pane menus through the shared `ViewList` with the command `float`, and a row runs `/float <view>`; a pane's own `⧉` button runs `/float` on that pane, as a float's `⊞` runs `/dock`.

19. **Translated text.** WiredFE's own text (never remote post content) comes from message catalogs in `src/i18n` (layer `i18n`: it may import `lib` and `config`; every layer above may import it). English (`src/i18n/locales/en.json`, imported statically) is the source and the fallback; `es`, `ru`, `ja`, `zh-Hans` and `de` are machine-translated from it by Prism, which owns those files: never hand-edit a non-English locale file (a hand translation goes in `.prism/exceptions.json`). They load on demand, one same-origin chunk each (`import.meta.glob`, so the CSP holds); a supported language with no file yet can be chosen and shows English messages (under its own `<html lang>`), and one whose file fails to load leaves English active. Messages are ICU MessageFormat strings with named arguments (`intl-messageformat`), so plural and select branches live inside one string and a translation can add the target language's own plural forms; i18next-style `_one`/`_other` keys cannot work, because Prism only translates the keys the source has. The catalog is nested objects, no root locale key, `lower_snake` keys, alphabetical within each object, one top-level namespace per area (`accounts`, `api`, `app`, `commands` with `defs` inside, `features`, `format`, `keys`, `state`, `ui`, `views`, `windows`), so parallel changes insert into separate regions. `t(key, values?)` (`src/i18n/translate.ts`) formats with the active language; `MessageKey` is the union of dot paths derived from the type of `en.json`, so an unknown key fails `tsc`. It falls back to English when the key is missing, the message does not parse, or its argument names differ from English's (a stale translation after the source changed); formatters are cached per language and key. Components call `useT()` (`src/i18n/I18nProvider.tsx`), which re-renders them when the language changes; plain code, such as a command formatting at run time, calls `t()`. `SUPPORTED_LOCALES` lists each language with its native and English name; `resolveLocale({ user, instance, browser })` (pure) picks the first supported of the reader's setting, the instance default and each `navigator.languages` entry (by language subtag: `de-AT` is `de`, any `zh-*` is `zh-Hans`), else `en`. `LocaleSetting` (`src/app/LocaleSetting.tsx`) feeds it the reader's `language` setting, the build's `defaultLocale` (`instance`; an optional BCP 47-style code in `wired.config.json`, which `tooling/loadConfig.ts` refuses to build unless it is a supported language) and the browser languages, and `<html lang>` follows the active language. The reader's choice is the `language` setting (`/lang`, WFE-310; a supported code or null for `/lang auto`), stored and synced with the desk like any setting (decision 17); `/lang`, the `Language…` row of the start menu and the `Ctrl+B L` / `Shift+l` hotkeys (which open the language list) all reach it (decision 6). A test changes language with `installFakeLocale` (`src/test/i18n.ts`), which installs an in-memory catalog; `setup.ts` puts English back after each test. `src/i18n/locales.test.ts` checks every locale file (JSON of nested objects of ICU messages) and deliberately does not ask a target language for every key or the source's arguments: they lag the source until Prism runs, the runtime falls back, and a source change must never turn CI red. **Rules every string follows:** never call `t()` at module load (the language is not known yet, and it changes), so a module constant such as `const NOT_A_FLOAT = fail('…')` becomes a function; a static field such as a command's `summary` or `usage` becomes a getter (`get summary() { return t('…'); }`), so it reads the current language whenever it is shown and `CommandDefinition` keeps its `string` types; whole sentences per key, never concatenated translated fragments. Never translated: command names, aliases, literal subcommand words (`move`, `size`, `list`), key chords, `@handles`, URLs, post labels and remote content. The first message converted is the refusal of `/as`, `/account switch|logout`, `/sync` and `/postas` for a handle the reader is not signed in as (`src/commands/notSignedInAs.ts`, key `commands.not_signed_in_as`).
